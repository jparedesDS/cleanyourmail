# CleanYourMail 1.2.0 — Validated Release Design

Date: 2026-11-10
Status: Proposed
Owner: jparedesDS

## Intent

Ship CleanYourMail 1.2.0 with the new Microsoft sign-in and the guided setup, after validating
Gmail and Outlook/Microsoft 365 with real accounts. This is the first release where the skill can be
handed to a non-technical person and the agent can walk them through connection without a manually
pasted token.

## Why now

The 1.2.0 code is merged but unreleased. Version 1.1.5 predates the Microsoft sign-in and the
`secret` command. The website already advertises one-click Microsoft sign-in, but
`PROJECT_CLIENT_ID` is empty and `docs/VALIDATION.md` is still `pending` for every provider. Shipping
without validation would make the site's claim false.

## Goals

- Register a public Microsoft client ID and make `connect outlook` work end to end.
- Validate Gmail (2FA + App Password) and Outlook/Microsoft 365 (device code) on dedicated accounts.
- Record `pass`, `fail` or `partial` in `docs/VALIDATION.md` without addresses, Message-IDs or secrets.
- Release 1.2.0: version, changelog, website `softwareVersion`, CSP hash if needed, tag and GitHub
  release.
- Update issue #2 with the results and close it.

## Non-goals

- App 0.3.0 (Microsoft sign-in in the desktop UI) — next project.
- Installer or signed binary — next project.
- Validating Yahoo, iCloud, Fastmail, Proton or custom IMAP — later, unless a test account is
  available now.
- Google OAuth — Gmail stays on App Password.
- Changing safety rules, deletion policy or the protected-mail list.

## Constraints

- Use dedicated test accounts. Never use a production mailbox for the first write test.
- No passwords, OAuth tokens, real addresses or Message-IDs in the chat, repo, issues, logs or
  screenshots.
- Moves use `--limit 5`; `undo` is verified before any unsubscribe. Unsubscribe uses `--limit 1` and
  is tested last.
- No permanent deletion, headers only, protected mail stays protected.
- The Windows, macOS and Linux CI matrix must stay green.
- The release is blocked until Gmail and Outlook both pass `doctor` and `undo`.

## Handoff

The owner performs the steps that need a browser or a phone: creating the accounts, enabling 2FA,
creating the App Password, registering the Microsoft application and approving the device code. The
agent runs the CLI commands, records the results and stops at the first unexpected error. The plan
marks each owner checkpoint explicitly; it never asks for a password or token in the chat.

## Validation scope and test data

- **Gmail:** run the sequence in `--mode folders`, then a second `plan --mode archive` with its own
  `apply --limit 5` and `undo`. Gmail archive is a distinct `X-GM-LABELS` path and must be covered.
- **Outlook:** validate one available account (personal Outlook.com or a work/school Microsoft 365
  account). The other audience uses the same device-code path but may require admin consent; the
  release notes qualify it instead of claiming it was separately tested.
- **Test data:** seed three to five newsletter-shaped messages with a `Date` at least 60 days old and
  a `List-Unsubscribe` header using IMAP `APPEND`. Do not lower `min_age_days` or relax any safety
  rule for the test. Do not use personal or transactional mail.
- **Non-technical walkthrough:** after the CLI pass, the owner follows the Phase 0 wizard on a fresh
  profile (no existing config or secret) and reports friction. A blocker found here is fixed before
  the tag; wording improvements can go into the release notes.
- **Other providers:** Yahoo, iCloud, Fastmail, Proton and custom IMAP are out of scope for this
  release. Their table rows stay `pending`.

## Approaches considered

**A. Release-first (chosen).** Validate the CLI and skill engine, then release 1.2.0. The app reuses
the same `oauth_ms` token store in a later 0.3.0 release.

**B. App-first.** Add the sign-in to the desktop app and ship everything together. Rejected: it
delays validation and builds UI on auth that has not been proven with a real account.

**C. Gmail-only release.** Validate Gmail, mark Outlook as beta and ship. Rejected unless the
Microsoft client ID cannot be obtained; see Contingency.

## Prerequisites (theirs)

| Prerequisite | Needed for | Fallback |
|---|---|---|
| Microsoft Entra tenant and app registration | Public client ID | Work/school tenant, free Azure account, or Microsoft 365 developer tenant |
| Outlook.com or Microsoft 365 test account | Outlook validation | New outlook.com account |
| Gmail test account with 2-Step Verification | Gmail validation | Enable 2FA on the secondary account, or create a dedicated account |
| Harmless test mail in both accounts | `apply` and `undo` | Seed three to five old newsletter-shaped messages via IMAP `APPEND` |

## Release gate

A provider is `pass` only when the full sequence in `docs/VALIDATION.md` succeeds:

`doctor` → `scan` → `report` → `plan` → `apply --limit 5` → `journal` → `undo` →
`unsubscribe --limit 1` → `rules`.

A provider is `partial` when `doctor`, `scan`, `plan`, `apply`, `journal` and `undo` pass, but
`unsubscribe` was not tested because no safe list exists, or `rules` could not be exercised. The
release may ship with a `partial` provider only if the limitation is written in the release notes
and the verification table. A `fail` on `doctor`, `apply` or `undo` blocks the release.

`unsubscribe` is irreversible. Never invent a list or unsubscribe from a real sender just to get a
`pass`. A provider is `fail` if a move is made and `undo` does not restore it.

## Contingency

- **No Microsoft client ID before the release:** hold 1.2.0. Immediately qualify the website so it
  does not advertise one-click Outlook while `PROJECT_CLIENT_ID` is empty; either remove the claim
  or label Outlook as "requires app registration". A docs-only 1.1.6 is the alternative, but it must
  not ship the 1.2.0 changelog.
- **Gmail 2FA cannot be enabled:** hold 1.2.0. There is no Google OAuth path in the code and
  `AGENTS.md` forbids one; the App Password path is the only Gmail path. Do not fake it.
- **A provider fails:** open a focused issue, add a regression test before changing a safety rule,
  and do not tag the release.

## Milestones

1. **M1 — Client ID and connection.** Register the app, set the client ID, run `connect outlook`,
   `doctor` succeeds.
2. **M2 — Gmail validation.** Enable 2FA, create the App Password, save it with `secret`, seed the
   test messages, run the full sequence in folders mode and the archive cycle, record the result.
3. **M3 — Outlook validation.** Connect the account, seed the test messages, run the full sequence,
   record the result.
4. **M4 — Non-technical walkthrough.** The owner follows Phase 0 on a fresh profile and reports
   friction; fix blockers before the tag.
5. **M5 — Release metadata.** Bump to 1.2.0, update the changelog, website `softwareVersion`, CSP
   hash if the JSON-LD changed, run all tests, tag `v1.2.0`, publish the release.
6. **M6 — Post-release verification.** Check the release page, README badge, website in both
   languages, and close issue #2.

## Calls made in this design

- Test data is synthetic: old newsletter-shaped messages via IMAP `APPEND`, no safety-rule override.
- Gmail validation includes both folders and archive modes.
- One Outlook account is validated; the other audience is qualified in the release notes.
- A provider may be `partial` when only `unsubscribe` is untested; `doctor`, `apply` and `undo` must
  pass.
- Gmail has no OAuth fallback. The App Password path is the only Gmail path.
- The non-technical walkthrough is an acceptance check, not a code deliverable.

## Open questions

- Which Microsoft tenant, Outlook account and Gmail account are available? Who owns the browser,
  phone and device-code steps? If none are available, M1 and M2 stop here.
- No fixed release date: the release happens when the gate is green.

## What is left to the builder

The exact commands, file paths, test names, owner checkpoints and commit boundaries belong in the
implementation plan. The design fixes the order, the release gate and the honesty rule: a provider is
not `pass` until `undo` succeeds.
